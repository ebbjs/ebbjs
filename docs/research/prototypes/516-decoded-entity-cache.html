Decoded entity cache — does it keep reads correct?

A throwaway logic prototype for issue #516. It models the server’s entity read/write protocol so you can push it through the awkward cases by hand. Nothing here is production code.

What this is asking

The server keeps one materialized copy of an entity in a read database (SQLite), and a dirty mark that tells readers “this entity may be behind the source of truth, re-materialize it first.” A read checks the mark, and if dirty it replays the missing actions, stores the result, then clears the mark — but only if the mark is still the one it saw. #516 wants to add a second, faster copy: a decoded cache keyed by entity id, filled when an entity is materialized and thrown away when it is written.

This prototype asks one question:

Does that second copy preserve the server’s existing correctness under (a) the dirty-mark compare-and-clear protocol, (b) concurrent materializations of the same entity finishing out of order, (c) provisional marks while a commit is in flight, and (d) the multi-writer rules? And what does eviction / memory pressure do to staleness?

  • The source of truth is where committed actions live. Each commit gets the next action # (the real system calls it a GSN).
  • SQLite is the materialized copy the server reads from today. Its last materialized action # is how current it is.
  • The dirty mark is either settled (a write completed and was not yet folded in) or provisional (a write is in flight). Marks carry an id so a materializer only clears the exact mark it saw.
  • The decoded cache is the new second copy: the already-parsed field map plus a last action #.

Rules to explore — flip these and watch correctness

Defaults are roughly the design as sketched in #516. The two that matter most are monotonic cache write and validate on read.
